# Strata on the Intel Arc Pro B70: the `b70` branch

This branch is upstream Strata (`main` at 7dd5cf1) plus the work that targets the Arc Pro B70 (Battlemage, `bmg-g31`, 32 GB)
on Linux with the `xe` driver. Everything below was measured on one B70 in a Ryzen 9 5950X box (64 GB RAM, PCIe
host-to-device probe 12.3 GB/s) on 2026-10-24. Nothing here is a claim from another machine.

## Speed against upstream

Setup:
- Model: Qwen3.8-Flash-Next GSQ-RCO IQ2_XS (ISTA-DASLab rev `ed59f92`), MTP draft, `--spec 4`, int8 KV, 32K resident KV.
- Memory: `--vram-reserve-mib 7168` (peak VRAM about 25 GB, because the card also drives the desktop), `STRATA_MIRROR_MIB=17000`.
- Each start: the page cache of every model file is dropped before the engine starts.
- Arms run in the order A B B A C C.
- Test: the `standard-v1` suite (`strata bench run`).

Medians in tokens/s:

| Arm | Prompt 4K | Prompt 16K | Decode short | Decode 4K | Decode 16K | Sanity |
| --- | ---: | ---: | ---: | ---: | ---: | :---: |
| A: upstream `main` + the one-line BMI2 build fix (it does not build without it) | 1,395 / 1,431 | 1,444 / 1,458 | 57.6 / 57.8 | 53.1 / 55.3 | 48.3 / 48.1 | 12/12, 12/12 |
| C: this branch without the community PRs | 1,494 / 1,497 | 1,500 / 1,500 | 57.0 / 57.0 | 54.0 / 50.4 | 51.8 / 52.7 | 12/12, 12/12 |

- Prompt: +12% at 4K and +17% at 16K. The fork's own work accounts for +3-6%; the community PRs add the rest.
- Decode at 16K: maybe +8%. The run medians don't overlap, but each is only 3 sampled answers and the per-request ranges overlap fully; treat it as unconfirmed.
- Short and 4K decode: no difference beyond noise.
- Greedy (temperature 0) answers were byte-identical in all six runs.

The numbers are for this branch, not for the fork's `main` as it was before this review. They are lower than community numbers on bigger hosts because of the 7 GB VRAM reserve and IQ2_XS. Compare the arms with each other, not with other machines.

## Upstream 0.1.54 (2026-10-30)

Upstream `main` 870aedd9 (engine 0.1.54) is merged, and its CUDA engine changes since the port's last re-migration
(0.1.40.1) are re-migrated into `sycl/` (commit 8adf90cc lists what came in and what stays off).
The port's kernels and B70 defaults stay; NVIDIA/AMD-only paths stay out.

Measured on the same box, nothing else running: Flash-Next IQ2_XS, a 118,196-token prompt (repo docs with a needle),
a ~850-token answer, temperature 0, `--spec 4`, int8 KV, 32K resident, reserve 7168 MiB, mirror 17,000 MiB,
`STRATA_PLE_AUTO_RAM=0`. Order: old 8192, new, old 16384, new, old 8192.

| Arm | Prompt tok/s | Decode tok/s | Needle |
| --- | ---: | ---: | :---: |
| `b70` before the merge, `--prefill 8192` (what setup wrote for 128K) | 1,761 / 1,762 | 60.8 / 60.8 | yes / yes |
| `b70` before the merge, `--prefill 16384` | 1,861 | 58.5 | yes |
| this branch, `--prefill 16384`, the B70 defaults below | 1,852 / 1,855 | 64.3 / 64.4 | yes / yes |

- Against the old branch as setup configured it: prompt +5%, decode +6%. The prompt gain is the 16K chunk (the old
  engine reads as fast with it); the decode gain is the engine (+10% against the old one at the same chunk).
- B70 defaults (`apply_b70_defaults`; a variable you set wins, `STRATA_B70_DEFAULTS=0` skips all):
  `STRATA_SELECT_LONG=1`, `STRATA_SPEC_COST=1`, `STRATA_PREFILL_AUTO_MAX=16384`, and the port's own decode kernels that
  were measured but left opt-in: `STRATA_IQ_DECODE_FAST=1` (bitwise), `STRATA_MMVQ_KREG=1`, `STRATA_HC_Q8=1` (both change
  the summation order; the answers stay equivalent, not byte-identical). Setup writes `--prefill 16384` for a Battlemage
  card with 24 GB or more above 32K context (GPU timeline of the 118K prompt: 78.6 s at 4,096, 74.6 s at 8,192, 68.5 s
  at 16,384, 66.7 s at 32,768, which borrows twice the cache).
- Fixed: a prompt whose last chunk is short (under 1,024 tokens: the routed-only expert walk) stalled for good in 2 of
  3 runs on an 8K prompt - the stager's claimed runs of 8 blobs held an early job back until a late job's buffer was
  free, and that buffer was freed by a DMA the launching thread queues after it needs the early job. Runs are released
  piece by piece now (4 of 4 clean).
- `use_root_sync` (dpct's cooperative launch: every work-group resident at once; none of these kernels has a grid
  barrier) came back with the re-migration on 41 launches the fork had stripped; stripped again.
- `STRATA_HC_Q8`: the BF16 copies of the hyper-connection projections stay (upstream drops them; the port's prompt-path
  view of the dropped rows made the 118K prompt's logits NaN).
- Parity tests: 62 of 63 pass on the B70 (`ple_parity` needs model files, as before).
- Opt-ins checked on the B70: `STRATA_PREFILL_LAYER_MAJOR=1` runs (118K, needle found) but reads the prompt slower here
  (1,447 tok/s: its experts take the FP16 path, not the int8 ESIMD kernels). `STRATA_PLE_COMPACT=1` works only with
  `--ple-io mmap` (the default direct I/O does not map the table; a line says so). `STRATA_GR_FUSED=1`: no gain.
  `STRATA_DEQUANT_SIDE=1` is refused: it stalls at a different layer each run under the Level Zero v2 adapter (it runs
  under v1 and with `STRATA_PREFILL_SYNC=1`), and the card's one compute engine leaves it nothing to overlap.
- Switching conversations after a long one now costs ~2-3 s once: upstream parks the decoded conversation before the
  next one overwrites it (#2526), so going back to it later does not read its prompt again.
- Not tested: two cards (the default two-B70 pipeline now runs upstream's N-stage loop), `--parallel` / batch serving,
  sampled-temperature speed with `STRATA_SPEC_COST`.

## Prompt speed round (2026-10-31)

New prompt-path kernels and a deeper expert staging ring, all for the B70. Measured on the same box: Flash-Next IQ2_XS,
the 118,196-token prompt, ~730-token answers, temperature 0, `--prefill 16384`, `--expert-cache auto`, the setup above.
Order A B B A.

| Arm | Prompt tok/s | Decode tok/s | Needle |
| --- | ---: | ---: | :---: |
| `b70` before this round (8dd45a8c) | 1,786 / 1,817 | 61.4 / 63.4 | yes / yes |
| this round | 2,911 / 2,935 | 64.9 / 64.6 | yes / yes |

- Prompt +62% at 118K, decode unchanged (within the runs' spread). An earlier A B B A while another process held 4 CPU
  cores: 1,613 / 1,549 -> 2,392 / 2,329 (+49%). The 8K diagnosis prompt under that load (A B A B): 1,018 / 1,390 ->
  1,391 / 1,770 tok/s. Prompts of 23-29 tokens: no difference.
- 15 runs of this default with prompt timing off (3 at 118K, 12 at 8K) and none stalled (see the prefetch note below).
- The short greedy answers are byte-identical to `b70`. The long answer differs from `b70` (the new attention, selection and
  expert kernels sum in another order) and is the same in both runs of this branch.
- GPU timeline of the 118K prompt with `STRATA_PREFILL_TIMING=1`: ~73 s -> 45.5 s.

| Phase (118K prompt) | Before | After | Change | Switch (B70 default on; `=0` off) |
| --- | ---: | ---: | --- | --- |
| QSA prompt attention | 14.2 s | 3.0 s | ESIMD kernel: INT8 DPAS scores (Q as 3 int8 limbs, exact), FP16 hi + lo P.V, 4 threads per (query, KV head) | `STRATA_PROMPT_ATTN_XMX` (3; 0: the per-cell kernel) |
| QSA selection | 7.6 s | 1.7 s | block scores on XMX with FP16 hi/lo splits (3xTF32-level) and the relu-sum fused; a candidate top-k (same ids as the full radix select) | `STRATA_SELECT_XMX`, `STRATA_TOPK_CAND` |

| Hyper-connection read | 5.2 s | 3.1 s | the up projection with the mix as its XMX epilogue, down and inject as one GEMM; the same bits for the mix | `STRATA_HC_UPMIX`, `STRATA_HC_DOWNINJ` |
| Routed experts (gemm gate/up + down) | 14.7-15.6 s | 9.6 s | FP16 products with the weights decoded in registers (IQ2_S / IQ2_XXS gate/up, Q2_0 down), one launch per group, 62-66 TFLOP/s, no FP16 copy of each expert; the int8 crossover is measured again (`|h1`) and now sits at 0-17 rows | `STRATA_PREFILL_F16X` |
| Expert copy waits ("dequant" + "wait copy") | 6.0-7.0 s | 6.6 s | with the faster products these grew to 12.9 s: the walk's grouped experts now get 64 more staging slots, so the copies overlap the products (a copy waited for the slot 24 back, which a group frees after its down product) | `STRATA_PREFILL_STAGE_AHEAD` (64) |

- **AOT builds and ESIMD registers.** A kernel's `grf_size<256>` property reaches the JIT ESIMD images but not the AOT
  ones (DPC++ 2026.1): they compiled in 128 registers and spilled. The FP16 expert products ran 11.4 ms instead of 0.76 ms
  per 16-expert group, the attention 11.7 ms instead of 4.7 ms per 2,048 queries. `sycl/CMakeLists.txt` now passes
  `-doubleGRF` to ocloc for Xe2 AOT builds (an ESIMD-backend option: the SYCL kernels do not read it). It applies to every
  ESIMD kernel: the int8 expert chain, which ran in 128 registers by accident in AOT builds, takes 1,700 instead of
  1,430 us per 16-expert group at 320 rows (`STRATA_I8_GRF` no longer changes it). On IQ2_XS that chain runs only below
  ~17 rows now; packs whose gate/up has no FP16 products yet (IQ3_S, IQ3_XXS, IQ4_XS) were not measured.
- **A cached crossover from a slow build stays.** `.strata-cache/i8-crossover.txt` keeps the int8 crossover per kernel
  revision; delete its lines when the expert kernels change.
- Opt-in, measured: `STRATA_PREFILL_PREFETCH=1` copies a large chunk's non-resident experts at each layer's MoE half,
  behind the queued attention / GDN work. From a worker thread it read the 118K prompt at 2,613 tok/s (vs 2,460), but the
  copy engine's queue stalled for good under the Level Zero v2 adapter once hundreds of its copies waited for compute
  events still to come (it ran under v1). The banked form in the tree waits on none and does not stall, but on the
  launching thread (~110 us of host time a copy) it read an 8K prompt at ~1,100-1,300 tok/s instead of ~1,800.
- Swept and left off (118K, `STRATA_PREFILL_TIMING=1`): `STRATA_GDN_XE=1` (recurrence 6.4 -> 9.1 s), `STRATA_GDN_KEYHEAD=1`
  (35 s, other bits), `STRATA_PREFILL_STREAM_ALL=1` (686-753 tok/s: host-bound staging), `--prefill 32768` (1,256 tok/s),
  `--prefill 24576`, `STRATA_STAGER_THREADS=16`, `STRATA_I8_MT=4`, `STRATA_EMB_REUSE_ACCOUNT=1`, `STRATA_PREFILL_MMQ=0/1`
  (all within noise or slower). `STRATA_PF_HCDOWN=1` ends the prompt with an error on SYCL (its kernel is a stub).
- Parity tests: 64 of 65 pass on the B70 (`ple_parity` needs model files). New: `esimd_f16_parity`, `gr_prompt_parity`;
  `qsa_prompt_attn_parity`, `gdn_parity` and `qsa_select_bench` check the new kernels against the old ones and FP64.
- Not tested: two cards, `--parallel`, other packs than IQ2_XS (the FP16 expert products take IQ2_S / IQ2_XXS gate/up
  with a Q2_0 down; other formats keep the old chains), FP16 or Q4_0 KV (the new attention takes INT8 KV only).

## Agent use and the second-turn hang (2026-10-31)

Measured with the [pi](https://github.com/earendil-works/pi) coding agent: one session, thinking `xhigh`, preserved thinking
(the template's default; pi sends each turn's reasoning back), a 64K-token system prompt (pi's own plus a 45K-token
`AGENTS.md`), `--max-context 262144`, `--vram-reserve-mib 3072`, the rest as above. Seven coding tasks in a copy of
`serve/` (read code, write and run pytest tests, edit a function, summarize): 52 requests, the context from 64,049 to
118,091 tokens, every task finished (the tests it wrote pass).

- **Every turn reused the cached history.** After the first prompt (64,049 tokens in 22.8 s), a turn read only its new
  tokens: 19 to 9,058, in 0.22 to 4.3 s (most under 1.5 s).
- **Answers at 74-111 tok/s** across 64K-118K (most 85-95).

**The hang it found, on this branch and before it (8dd45a8c):** any prompt that continues a conversation - an agent's or
a chat's next turn, the chunk after the cached prefix - stopped for good at an early layer (2-5) of its first chunk. A
two-turn chat at 15K hangs the same way, every time; a new conversation never did, which is why the benchmarks above
did not show it. The host waits in `queue::wait()` at the layer's routing with both GPU engines busy. With
`STRATA_PREFILL_TIMING=1` or `STRATA_PREFILL_SYNC=1` the same runs finish, so the engine now runs the prompt timing's
marks, folds and drains on every prompt without printing them (`STRATA_PREFILL_ORDER`, default on; `=0` restores the
old behaviour): 118K 2,911 / 2,935 -> 2,861 / 2,857 tok/s (-2%). The cause is not found yet. Ruled out: the deeper staging
ring, the lean exchange, the verify device plan and no-host mode, the MTP draft layer, DMA of every expert, blocking
refills, the lend mirror, the copy engine (off), the Level Zero v1 adapter (it hangs earlier), a barrier before the
routing download or before each cross-queue wait, a drain of either queue at the chunk's start, polled drains.

### 256K (2026-10-31)

- **One prompt of 249,618 tokens** (the README's test with more of the same docs, `--max-context 262144`, 7 GB kept
  free): 2,750 tok/s prompt (91 s), 64.6 tok/s answer, the fact in the middle found; within 4% of the 118K speed.
- **pi from 170K to 245K and through a compaction**, settings as above (3 GB kept free): a 156K-token `AGENTS.md`
  (170K-token first prompt, 58.7 s), eleven tasks, 82 requests. pi compacted at 245,165 tokens (two summary requests,
  30K and 0.3K tokens, other system prompt), then went on from 195K to 225K. Every task finished; the tests it wrote
  pass. Turns read 15 to 26,065 new tokens in 0.19 to 11.1 s (64 of 79 under 1.5 s); answers at 73-103 tok/s (median
  87). Lowest free VRAM 3,312 MiB, lowest free RAM 25 GB.
- **Fixed on the way (992759c6): the system prompt's end checkpoint.** The checkpoint retention pinned the chain's
  shortest checkpoint as its root. With a system prompt longer than `--prompt-cache-every` (16,384) that is a periodic
  checkpoint inside the system prompt; the one at its end rotated out after a few turns, so a new chat with the same
  system prompt read nearly all of it again. The first 256K session's post-compaction prompt reused 16,384 of 195,051
  tokens (59 s); after the fix 169,579 of 195,644 (11 s). Repro (41K-token system prompt, six turns, an unrelated chat,
  a new chat): 16,384 reused in 10.2 s before, 40,704 in 1.0 s after. The checkpoint at the system prompt's end is now
  marked (`ConversationCheckpoint::root`) and never evicted; it does not keep a parked conversation parked the way a
  `pin=N` prefix does. `--session-save-reclaim` frees it only after every other unpinned checkpoint (66aba3c3).
- **Fixed after (66aba3c3): no park at a task boundary.** A new pi task sends the last reply back without its
  thinking, so the engine rewound by that reply (93 to 1,014 tokens) and parked the whole conversation for it: five
  times in the first session, 2.2-2.5 s and 3.6-4.5 GB each at 183K-237K, every copy superseded by the next. A prompt
  that goes on from the live conversation's own checkpoint and leaves at most 4,096 tokens (and 1/16 of it) behind no
  longer parks (`--conversation-cache-park-tail N`, `0` = as before). A 118K system prompt, one task boundary: 2,289 ms
  -> 658 ms. A branch 5.5K tokens past the system prompt still parks and comes back from the cache. The pi session
  again: eleven tasks, 64 requests, 170K to 245K, the compaction, then 188K to 200K. Every task finished. The one task
  boundary that rewound skipped the park (a 414 ms turn); the compaction still parked, and the next turn still borrowed
  169,579 tokens (18,097 new read in 9.4 s). Lowest free RAM 27 GB.

### Agent speed at 200K (2026-10-31, night)

Where a 256K pi session spends its time (a rerun of the session above, 64 requests): 395 s generating (73%), 145 s reading prompts
(the cold 170K start 60 s, the summary request after the compaction 13 s, every other turn 70 s).

- **Fixed: a checkpoint at each turn.** A turn checkpoint copies 118 MB of DeltaNet state to the host. The copy took
  77.5 ms, 59 ms of it faulting in a fresh vector, on every turn. The B70 defaults now turn on upstream's opt-ins for
  this: `STRATA_CKPT_ASYNC`, `STRATA_CKPT_POOL` with two ready vectors, `STRATA_CKPT_GATHER`. A small turn (17-23 new
  tokens) went from 195-236 to 104-149 ms at 203K, and from 190-212 to 109-135 ms at 118K. The save is now 5 ms. The
  text was byte-identical with the switches off and on. Decode does not pay for it: with the expert cache held at about
  16,290 slots, the 200-token replies after those turns decoded at 77.2-81.6 tok/s with the switches off and 78.6-84.7
  with them on (two runs with the automatic cache size had shown a 3% gap the other way: run-to-run spread). The VRAM
  stage (118 MB) is now priced into the automatic cache size, so the card still ends with the reserve it was asked for.
  `STRATA_CKPT_VRAM_SLOTS` and `STRATA_PARK_ASYNC` stay off: they keep VRAM down to 1.5 GB free, and a restore costs
  about 12 ms here anyway.
- **Explained: the slow turns of the turns script at 217K** (1.5K tokens in about 4 s). Every one of those turns
  rewound by the last reply and parked the whole conversation (2.2-2.6 s). That is the task-boundary park fixed above.
- **Measured, not changed: decode is bound by kernel time.** With the timers off, a decode window at 203K takes about
  27 ms: the verify pass about 24 ms, the MTP draft about 3.2 ms, everything on the host under 0.3 ms. At 8K the verify
  pass is 22.7 ms, and a device trace (unitrace) puts the kernels at the same 22-23 ms, so there are no gaps to close.
  Per window, the routed experts take about 7.5 ms at roughly 300 GB/s (the card's peak is 608 GB/s), the dense IQ4_XS
  projections 4.6 ms at about 350 GB/s, the hyper-connections 2.8 ms, and about 660 small kernels under 6 us add 1.9 ms.
  Tried without gain: 1 or 4 rows per lane in the expert kernels instead of 2 (5-15% slower), an unrolled block loop,
  counter-based Level Zero events. The next step is a rewrite of the IQ2_S / Q2_0 expert kernels.
- **Profiling skews the decode figures.** `STRATA_VERIFY_PROFILE` and the other GPU stage timers slowed the same decode
  from 78 to 56 tok/s and made small turns look 2-3x slower. Use `STRATA_DECODE_TIMING` (host clock) or unitrace
  (`--teardown-on-signal 15`, and stop the container with `docker stop` so it writes its summary).
- **Fixed: the XMX selection past ~201K.** The prompt's block scores run on XMX with the chunk's keys split into the
  attention scratch. Past 50,371 key blocks (about 201K tokens) the split keys (26.55 MB) no longer fit in the scratch
  (26.16 MB), so every later chunk took the GEMM tiles, which were about 4.5x slower at 118K. A pi session at 243K hit it
  (found by the new fallback line). The scratch is now sized for the context's last key block: about 34.5 MB at 262K.
  The 249,618-token prompt (the README's 250K test, one run each): 2,750 -> 2,832 tok/s, the needle found, no fallback
  line. That run also has the checkpoint defaults, which make the checkpoints taken during the read cheaper, so not
  all of the 3% is the scratch. Its answer decoded at 62.4 tok/s against 64.6: its automatic expert cache got 12,920
  slots against 13,225 (the size follows what the desktop holds in VRAM at start).
- **The pi session again**, with the checkpoint defaults (before the selection fix) and every timer off: eleven tasks,
  90 requests, 170K to 244K, the compaction, then on to 223K. Every task finished. Small turns (100 new tokens or fewer)
  took 344 ms on average, against 418 ms before. Five task boundaries skipped the park, the compaction still parked, and
  the next turn still borrowed 169,579 tokens. Decode 86 tok/s. Lowest free VRAM 2,922 MiB (3,312 in the first session;
  the checkpoint stage is 118 MB of it): the engine itself then held 28,610 of the card's 32,656 MiB, the desktop about
  1.1 GB. Lowest free RAM 26 GB.
- Not taken: the `STRATA_PREFILL_ORDER` cost (-2% prompt speed; the hang it works around still has no root cause), and
  wider prompt windows for reads of up to 64 tokens (6 to 8 tokens a window: about 1-2 s per session).

with thinking off, so 85 to 93% of its guesses hold.  Where fewer hold the wider window does not pay and the engine stays on 3 to 4

reasoning-v1 122.3 tok/s at `--spec 4` and 124.3 at `--spec 6` with the switch (77% of guesses hold), code-v1 103.8 and
104.1 (63% hold).  Expect the same from agent traffic at a temperature (62% held over a day of it): no loss, no real gain.
There the 14 ms a window costs before its first row decides the speed.

`STRATA_SPEC_PROBE_MIN=1` (off by default; Settings: "spec_probe_min") changes how the engine prices a window size it has
hardly used.  The first use of a size in a context range is about 20 ms slower than the ones after it.  Without the
switch the price of a size is the average of its first three tries, and the draft layer never times a size again once
those are spent, so a size can stay priced out until the engine restarts: that is the `--spec 4` row above, held at 3
rows for the whole 8K run.  With it the price is the fastest of the first tries, a try stands even when a wider window
looks better, and a size not timed for `STRATA_SPEC_STALE` checks (300) is timed once more.  `STRATA_SPEC_PROBES` (3) is
the number of tries.  The text is the same either way.  `STRATA_SPEC_COST_TABLE` (start prices) is now read by the server
too, not only by the command-line bench.

### Where a window's time goes, and what is left in the kernels (2026-11-10)

7.7 ms (qkv 1.9, out 1.9, z 1.2, q 0.9, shared expert + quantize 1.9), hyper-connection reads 3.5 ms, router + plan

### Other expert formats: one kernel for all of them (2026-11-11)

## Pictures on one B70 (by hand)

Pictures are off in the served setup. This is what they need, so a config made by hand can turn them on. The first picture
on a B70 once reset the card in October (INTEL.md, "Pictures on an Arc"); the cause was not found.

Tested 2026-11-11 on the served UD-IQ1_S pack with the CPU reader (Unsloth's `mmproj-BF16.gguf`, 300 tokens a picture, 8
threads), one start, four requests: a 448x448 picture with a line of text and three shapes, the same picture again, a plain
text question, a second picture. All four answered, with the text and the shapes right. The first picture took 2.6 s for the
whole answer (228 prompt tokens, 196 of them the picture), the same picture again 0.5 s (221 of 228 tokens reused), and the
kernel log had no `xe` fault. The reader alone encodes that picture in 2.7 s and holds 1.0 GB of RAM while it runs. Larger
pictures, several pictures in one request and a long session with pictures were not run.

- **Path:** the server decodes the picture and hands it to `strata-vision` (llama.cpp's mtmd, on the host, CPU). That writes
  `<n tokens> x 2560` floats. The server joins the pictures of a request into one file in `/dev/shm` and names it on the
  engine's `GENI` line. The engine, in the container, opens that same file, so `STRATA_SYCL_SHM` must stay `1` (default). The
  engine needs `--vision` in its args; the server adds it when the config has a `"vision"` section.
- **Files:** `strata-vision`: `./setup.sh --backend sycl` builds it into `engine-sycl/`. By hand: put llama.cpp at the commit
  of `LLAMA_CPP_COMMIT` (setup.py) in `third_party/llama.cpp`, then `cmake -S tools/vision -B build-vision -G Ninja
  -DCMAKE_BUILD_TYPE=Release -DLLAMA_DIR=third_party/llama.cpp -DSTRATA_PORTABLE=OFF` and `cmake --build build-vision
  --target strata-vision` (the program is `build-vision/bin/strata-vision`). The picture file is
  `mmproj-Qwen3.8-Flash-Next-BF16.gguf` (907,543,008 bytes). Unsloth's own `mmproj-BF16.gguf` holds the same tensors
  (QUANTS.md, "Images"). The paths in `"vision"` are host paths, not container paths:

      "vision": {"exe": "<repo>/engine-sycl/strata-vision", "mmproj": "<folder>/mmproj-Qwen3.8-Flash-Next-BF16.gguf",
                 "model": "<first shard of the model>.gguf", "gpu": false, "max_tokens": 300, "threads": 8}

- **Limits:** `lazy_load` is refused together with `"vision"` (serve/runconfig.py). A full `/dev/shm` (or `STRATA_SYCL_SHM=0`) ends in `ERR cannot open <file>`
  from the engine, because the container sees only the host's `/dev/shm`. `STRATA_VISION_DIR=<folder, no space>` (default unset) moves
  the reader's folder and the fallback file there; `strata-sycl.sh` mounts it at the same path, and `sycl/serve/server_intel.py`
  says so in the log when a picture file lands where the container cannot read it.
- **Cost:** no VRAM (the engine adds a position table of `3 x (max-context + 64)` int32, 3 MB at 262,144). Host RAM: the
  picture file about 0.9 GB while the reader runs, and 2,560 floats per image token on top: at the CPU limit of 300 tokens
  3.1 MB per picture (at 1,024 tokens 10.5 MB), also in `/dev/shm` while a request runs.
- **Speed:** 1.7 s for a 448x448 picture on an A750's host (INTEL.md); on this B70's host (Ryzen 9 5950X) the numbers above.

## Run-config keys on the Settings page

The web page's Settings view edits a short list of keys of the run config (`strata-<model>.json`); a change is used from the
next start. Besides `vram_reserve_mib`, `conversation_cache_slots`, `conversation_cache_mib` and `parallel` it lists:
`conversation_cache_spill_dir` (the SSD tier: a folder as the engine sees it, in the container the folder that holds the repo
is `/work`, e.g. `/work/strata-spill`; empty removes the tier and the next two keys), `conversation_cache_spill_mib` (quota,
engine default 24576) and `conversation_cache_spill_min_free_mib` (disk kept free, engine default 40960), and `batch_mtp`
(`--batch-mtp`, one draft proposal per parallel request; refused unless `parallel` is 2 or more, and dropped when `parallel`
goes off). Empty means the engine default and takes the flag out of `args`.

The SSD tier costs time: a conversation comes back slower from the drive than from RAM (about 0.3 s for 150K tokens). The
first start with a spill folder measures that drive once: 1 GiB is written, flushed and read back with the tier's own
block I/O (at most 3 s each way), and the result is kept in `<folder>/drive-speed`. Every start then writes one log line
(`conversation cache: SSD tier drive: reads N MB/s, writes N MB/s ...`) with the seconds 1 GiB of a parked conversation
takes to come back and to write, and the Monitor's Conversation cache card shows the same under "From the SSD". The
restore-or-read gate uses the measured read speed (`--conversation-cache-spill-mbps N` sets another). Delete the file to
measure again. Measured on this PC (1 GiB, direct I/O; the engine's own first start on the NVMe gave 3,199 and 2,224 MB/s):

| Drive | Reads | Writes | 3 GiB back | 3 GiB written |
|---|---|---|---|---|
| NVMe | 3,224 MB/s | 2,137 MB/s | 1.0 s | 1.5 s |
| SATA SSD (Samsung 870) | 505 MB/s | 395 MB/s | 6.4 s | 8.2 s |

A 1 GiB file shows the drive's burst write speed; a longer write on a drive with a small fast cache can be slower.

`conversation_cache_park_ssd` (`--conversation-cache-park-ssd`, needs the spill folder) parks on the SSD only: every parked
conversation goes to files in the folder and none stays in RAM, and no K/V copy of the live conversation is kept for the
next park. More agents can then take turns on the one stream without more memory.

How a park works: a conversation has its K/V in `c<N>.kv` (every part at a fixed place with room for the largest context;
the file is sparse), its running state in `c<N>.meta`, and each checkpoint in its own file `c<N>.k<tokens>-<hash>`. A
checkpoint never changes once taken, so its file is written once. The folder has to be on a filesystem that keeps sparse
files (ext4, xfs and btrfs do; on exFAT or FAT32 the K/V file is refused and the park is skipped with a log line). A conversation that is read back keeps its files. Its
next park writes the meta file again (about 113 MiB), the checkpoints that are new (about 113 MiB each, usually one a
turn) and, into the K/V file, only the bytes that changed since: the tokens it read and wrote in between, at about 15 KB a
token. The K/V goes from where it lives straight into the file, with no copy in RAM. The park is synchronous: the engine
does not run the session before the files are whole. The index records the order that makes a stop safe at any point: an
entry's record is deleted before its files change and written again after all of them are whole.

Settings (all under the spill folder, all optional):

| Key | Flag | Default | What it does |
|---|---|---|---|
| `conversation_cache_park_ssd` | `--conversation-cache-park-ssd` | off | park on the SSD only |
| `conversation_cache_park_ssd_whole` | `--conversation-cache-park-ssd-whole` | off | write the whole conversation at every park (about 3 GiB at 150K tokens) instead of what changed |
| `conversation_cache_park_ssd_keep_pct` | `--conversation-cache-park-ssd-keep-pct N` | 50 | update a file in place when at least N% of its tokens still hold; below it a new file is written and the old one stays |
| `conversation_cache_park_ssd_deepest_checkpoint` | `--conversation-cache-park-ssd-deepest-checkpoint` | off | keep only the deepest checkpoint; by default every checkpoint has its own file, written once (about 113 MB each) |
| `conversation_cache_park_on_exit` | `--conversation-cache-park-on-exit` | off | park the conversation in use at a clean stop, so the next start reads it back from its file |
| `conversation_cache_park_ssd_checkpoints` | `--conversation-cache-park-ssd-checkpoints N` | 0 | 0: every checkpoint keeps its file; N: the shallowest one (the start new conversations share) and the N deepest |
| `conversation_cache_park_ssd_stream` | `--conversation-cache-park-ssd-stream` | off | a read-back copies the K/V from its file straight into the session, block by block, instead of reading the conversation into RAM first |

What it costs:

- A switch takes the drive's seconds instead of about 0.3 s. Measured live with whole-conversation parks (NVMe, 3,199 MB/s
  read): a 109K-token conversation came back from its 2.4 GiB file in 1.17 s, plus 0.46 s to restore it.
- Every checkpoint is kept, each in its own file that is written once, so a rewind costs what it costs in RAM. With
  `deepest_checkpoint` only the next turn's resume point is kept: measured, a request that rewound a 69K-token
  conversation to before that checkpoint read all 69K tokens again (25 s).
- RAM is used only during a switch: the incoming conversation until it is restored.
- `STRATA_SPILL_STORE_VERIFY=1` is a test switch: after every park the K/V file is read back and compared, byte for
  byte, with the bytes it was written from (`STORE_VERIFY ok` or `FAILED` in the log; a file that differs is removed).
  It reads the whole file each time.

Measured on the B70 (NVMe at 3,199 / 2,224 MB/s, two conversations of 20K and 24K tokens taking turns through the server,
`STRATA_SPILL_STORE_VERIFY=1`): 7 parks, 2 whole and 5 in place, every one `STORE_VERIFY ok` over 298-352 MiB of K/V. A
whole park wrote 524-577 MiB in 0.65-0.70 s. A park in place wrote 226 MiB (0.4-0.8 MiB of K/V for 20-40 new tokens,
225 MiB of running state and checkpoint) in 0.37-0.44 s. A read-back took 0.30-0.58 s for the 0.5 GiB files and the
restore 0.08 s, so a switch cost about 0.8 s on top of the request (the verify switch adds its own read).

Larger ones, same switch on, 40 parks in all with none differing: a worker's 143K-token conversation was written whole
once (2,310 MiB, 2.1 s) and its next park wrote 244 MiB in 0.31 s (17.7 MiB of K/V for 1,208 new tokens); it came back in
1.0-2.1 s plus 0.3 s to restore. With every checkpoint in its own file (two conversations of 69K and 90K tokens): the
first park wrote 5-6 checkpoints (677-790 MiB of state beside the K/V, 2.0-2.4 s), every later park wrote one new
checkpoint and the meta file (226 MiB, 5 kept) in 0.65-0.77 s, and a read-back of the 1.7-2.1 GiB took 1.0-2.2 s. A
request that rewound the 69K-token conversation to before its last turn took 0.3 s; with only the deepest checkpoint kept
(`deepest_checkpoint`) the same request read all 69K tokens again (25 s). With `park_on_exit` a restart parked the
conversation in use in 1.2-1.4 s, and after the start conversations came back from their files in 1.9 s and 3.4 s (25-31 s
to read them again). A park lends the live checkpoints to the file writer instead of copying them (about 113 MiB each):
that took the park in place from 0.65-0.77 s to 0.26-0.27 s and its RAM from about 0.8 GiB to the running state's 0.1.

`park_ssd_stream`, same two conversations: a switch took 2.0-2.1 s in all (0.81-0.85 s to read the meta and the six
checkpoint files, 677 MiB; 0.49-0.50 s to park the outgoing one; 0.57-0.67 s to stream 1.0-1.3 GiB of K/V into the session
and restore the state), and only the checkpoints were in RAM, not the K/V. Checked with `STRATA_SPILL_STORE_VERIFY=1`: 8
streamed restores and 7 parks, none differing. That check leaves out one row: the indexer's last row of each layer (the
moving spare row, 512 bytes) is built again from the running state by every restore, and in 2 of 8 restores what it
built differed from the parked bytes there and nowhere else, the same through RAM and streamed.

With `park_ssd_checkpoints 2` on top (three checkpoint files instead of six, 338-451 MiB): a switch took 1.2-1.5 s in all
(0.33-0.45 s to read the meta and the checkpoints, 0.25-0.26 s to park, 0.42-0.52 s to stream the K/V and restore);
7 parks and 8 streamed restores checked, none differing; the rewind to the previous turn stayed at 0.3 s.

Two server settings for agents (run-config keys, both off by default):

- `stream_linger_s`: when the agent that was just served has a tool running, the other agents' requests are held back up
  to this many seconds for its next request; if it comes in time there is no switch. `/metrics` `threads.return_gap` says
  how fast agents come back (median, 90th percentile, how many within 1 s and 3 s), `lingered` and `linger_kept` how
  often the wait began and paid off. Not measured on real traffic yet.
- `tool_name_repair: prefix`: a call for a tool the request did not declare is read as the one declared tool whose name
  it extends, or that extends it, at an underscore (`process_manage` for `process`); with two candidates nothing is
  guessed. `/metrics` counts them as `tool_names_repaired`.

The automatic size of the RAM for parked conversations (no `conversation_cache_mib`) is `conversation_cache_auto_pct`
percent (default 40) of the RAM free above `conversation_cache_min_free_mib`, at most `conversation_cache_auto_max_mib`
(default 8192). That RAM also holds a copy of the conversation in use, so two agents taking turns need room for two
conversations: a budget of 5632 MiB with two conversations of 150K and 190K tokens skipped every park ("snapshot ...
exceeds available budget") and each switch read 130-150K tokens again (42-50 s). The Monitor's Conversation cache card
counts skipped parks by reason. `STRATA_MIRROR_MARGIN_MIB` (default 4096, Settings: `expert_copies_margin_mib`) is the
RAM the automatic cap on the expert copies leaves free.


### More keys on the Settings page

The page shows its keys under headings (Model and context, Speed, Parked conversations, SSD tier, Thinking and answers,
Server, Monitor). Every key below is empty by default: empty takes the flag, the variable or the key out of the run config
and the default applies. A value is checked before it is saved, and a start without the key behaves as before. Engine flags
are kept in `args` and `user_args`, engine variables in `env`, server numbers as top-level keys read at start. `kv_format`,
`max_context`, `kv_resident` and `mtp_window` are part of a saved conversation's identity: changing one drops the
conversations saved on the SSD tier at the next start.

| Key | Flag, variable or server | Default | What it trades |
|---|---|---|---|
| `max_context` | `--max-context N` | 4096 | RAM and VRAM grow with it; a length the card cannot hold stops the start |

recipe; his config also holds settings of his own machine, which setup does not write):

| Part | Value |
| --- | --- |

| Model files | `unsloth/Qwen3.8-Flash-Next-GGUF`, folder `UD-IQ1_S`, three shards, revision `084c631` (2026-11-07); sizes and SHA-256 are pinned in `setup.py` (`UNSLOTH_IQ1_S_SHARDS`). The other Unsloth sizes stay at their older revision |
| Layer 18 graft | `blk.18.ffn_gate_exps.weight` of shard 2 is IQ2_S in the published file and IQ2_XXS in UD-IQ1_M; `tools/iq_pack.py` needs one type for gate and up. Setup reads that one tensor (216,268,800 bytes) from UD-IQ1_M's shard 2 by HTTP range request, checks its SHA-256, writes it over the old one (which was larger: the rest of the slot becomes zeros), changes the tensor's type in the header, and checks the whole shard against the pinned SHA-256 of the result. Offsets and file size do not change. Idea: hum-ma (hum-ma/Qwen3.8-Flash-Next-UD-IQ1_Strata-GGUF). Run it by hand: `python3 tools/graft_tensor.py --help`. The smaller tensor leaves a 52,428,800-byte hole in the file. Strata follows the header's offsets and does not mind; llama.cpp refuses the file (`tensor 'blk.18.ffn_gate_inp.weight' has offset ..., expected ...`). Needed only if you also want to load the file in llama.cpp: `python3 tools/graft_tensor.py --target <shard 2> --compact --expect-size 37515666848` moves the 753 later tensors down (22.3 GB written), rewrites their offsets and cuts the file to 37,515,666,848 bytes. It works in place and is restartable (a journal `<shard>.compact`; run the same command again after an interruption; the file is unreadable until it finishes), and it changes the shard's hash. A rerun of setup recognises a compacted shard by its size (the pinned `compacted_size`) and a header with no holes, and then does not check its SHA-256 (none is pinned for it); a pending `<shard>.compact` journal makes setup stop and tell you to run the same `--compact` command again. The tool refuses a symlink or a file with other hard links (it writes in place); setup copies such a shard first (a reflink where the filesystem has them). Off by default |

## Build and run

    docker build --pull -t strata-sycl-dev sycl/tools
    docker run --rm -u $(id -u):$(id -g) -v "$PWD/..:/work" -e AOT=bmg-g31 -e REPO=/work/Strata \
        -e BUILD_DIR=/work/Strata/build-sycl-aot strata-sycl-dev "cd /work/Strata && bash sycl/tools/build.sh strata"

`build.sh` with no target builds `strata` only. The kernel parity programs, tests and benches are off by default (each compiles its own
device code, which is most of the time of a full build): `PARITY=ON bash sycl/tools/build.sh <target>` builds one, `... all` every one;
`ctest` then runs them on the card. `DSV41=ON` adds the unmaintained `strata-dsv41`. The small host-only tests
(`conversation_spill_test`, `draft_policy_test`, `gated_proposal_test`, `spec_admission_test`) are always configured. A build folder keeps its cache: a
folder made before this change keeps PARITY=ON until `PARITY=OFF` is given.

`HOST_MARCH` (CMake `STRATA_HOST_MARCH`) sets `-march` for the engine's own host C++ code, not for ggml and not for the device code.
Empty (default) is the baseline x86-64. `x86-64-v3` (AVX2, FMA, BMI2) is for a build that runs on any CPU since Haswell / Zen 1. `native`
is for a build that stays on the PC it was made on. The files that carry their own `-mavx512*` or `-mno-avx2` options keep them. The
gain is unmeasured and probably small, since much of the host time is spent in Level Zero calls.

Serving works as in `docs/INTEL.md`.

A one-shot `strata generate` with `--mtp` gives the draft layer's buffers back before `main` returns (upstream PR #5161).
Before that, `--spec 4` with a reply of a few hundred tokens could end in a segfault (exit 139) after the whole summary
had printed: the drafter's destructor freed device memory while the runtime was already shutting down. Regression test:
`sycl/tools/test_mtp_teardown.sh` (`STRATA_BIN=... MODEL_ARGS="..."`).

On a 64 GB desktop:
- Leave `--ple-io` at its default (`direct`); `ram` locks the 28.8 GB PLE table.
- Set `STRATA_PLE_AUTO_RAM=0` (engine 0.1.54+): the PLE residency policy locks that same table in RAM whenever table +
  expert mirror + 8 GiB are free at load, and apps opened afterwards then run the desktop out of memory.
- Size `STRATA_MIRROR_MIB` so at least 7 GB stays free.
