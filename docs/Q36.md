# Qwen3.8-27B on one Arc Pro B70: the dense family of `strata`

A second model family in the one `strata` binary, for the **dense** [Qwen3.8-27B](https://huggingface.co/Qwen/Qwen3.8-27B) (GGUF
architecture `qwen35`) on the same card. There is no `strata-q36` binary any more: `strata` reads the architecture of the GGUF it is
given and runs the Flash-Next engine ([B70.md](B70.md)) for `qwen4exp` or a pack, and the dense engine for `qwen35`. `Q36=OFF` builds
`strata` without the dense family; that is the Flash-Next-only binary the fork had before the merge.

**What is merged and what is not.** Merged: the binary and its entry point (the family switch is the first statement of `main()`), the
serve protocol and `serve/server.py`, the kernel libraries, the GGUF reader and the family headers, the build and the serve wrapper.
**Not merged:** the dense family still runs on its own driver inside `q36_engine.dp.cpp` (its serve loop, its sessions and prefix-reuse
conversation cache, its batch slots and MTP window). It does not run on Flash-Next's `Session`, conversation cache and scheduler
classes: those are built around Flash-Next's layers (hyper-connections, experts, the expert cache, the verify plan), and putting the
27B's decode path on them would change every step of it, which needs the card (token-for-token, KL, graphs). The 27B's decode
kernels stay in their own sources and libraries (`q36_mmvq_dense`, `q36_xr_dense`, `libq36_w4.so`, `libq36_tla.so`).

**Status by this fork's bar** (128K-256K context, at least 1,000 tokens/s reading the prompt, at least 10 tokens/s answering):
**experimental.** By that bar it is usable to about 128K (a 118K-token prompt read at 1,096 tok/s) and not at 256K (721 tok/s,
2026-11-03). For everyday use on this card it is ahead of llama.cpp and still behind vLLM: a request as a client sends it
(sampled, thinking on) answers at about 75 tok/s and a greedy one at 65-81, against 44-48 for llama.cpp's best runs and about
110 for vLLM. The whole model is in VRAM.

This tree got the engine by a port from the branch it was written on. It was built and run here on 2026-11-11 (the first table
below). The second table is from the original branch on 2026-11-03 and was not measured again.

## What it is

- `sycl/src/qwen35/q36_engine.dp.cpp` (the engine), `q36_kernels.dp.hpp` (its decode kernels), `q36_prefill.dp.hpp` (prompt attention
  and the prompt's GDN recurrence), `q36_tla_fmha.cpp` (the long-prompt attention library), and `src/qwen35/` (a
  host-side requantizer). `strata::qwen35::run()` is its entry point; `include/strata/qwen35/dispatch.hpp` is the family switch. It began as a SYCLomatic migration of a CUDA engine and has been edited by hand since.
- It speaks the same serve protocol as `strata` (`READY`, `GEN`, `T`, `DONE`, `STOP`), so `serve/server.py` serves it with
  `sycl/serve/strata-sycl.sh` and the usual API.
- It links the same kernel libraries as `strata`, which are not changed for it. The decode kernels it tuned for the 27B's shapes
  (the 17,408-wide `ffn_down` read in two pieces or two parts, a persistent grid for every format, KREG for Q3_K and IQ4_NL, an SLM
  table for the wide IQ4_NL kernel) are `sycl/src/qwen35/q36_mmvq_dense.dp.cpp`, a source of the dense family only (listed inside the dense block of `sycl/CMakeLists.txt`): the engine calls it
  first and `native_mmvq` for what it declines. The few lines of shared headers that know the dense family sit behind
  `STRATA_Q36_BUILD`, which the build defines for every target when the family is built in (an inline function has one definition in the
  binary). Without it (`Q36=OFF`) `strata` is compiled from the same sources as before the merge
  (`tools/check_q36_isolation.py` and `tools/test_q36_build_wiring.py` check it).
- **The family switch.** `main()` calls `strata::qwen35::serves_dense(argc, argv)` first: it reads only the header of the file `--native`
  or `--model` names. A `qwen35` file goes to `strata::qwen35::run()`, before any Flash-Next state, stdout mode or B70 default exists, so
  the 27B starts as `strata-q36` started (same flags, same serve protocol). Every other file takes the Flash-Next path unchanged.
  A file that cannot be read is left to the Flash-Next path, which reports it. `strata --families` prints `qwen4exp qwen35` for this build.

## Model files

Unsloth's [Qwen3.8-27B-GGUF](https://huggingface.co/unsloth/Qwen3.8-27B-GGUF): `Qwen3.8-27B-UD-Q4_K_M.gguf` (16.5 GB) and
`Qwen3.8-27B-UD-Q4_K_XL.gguf` (17.6 GB; it carries one IQ3_S `ffn_down`, which the native kernels take). The MTP block (`blk.64.nextn.*`) is in the
same file. 64 layers plus the MTP block, 5,120 wide, a 17,408-wide FFN, 24 query heads over 4 KV heads of 256. No other file is
needed.

## Build

`strata` is built the way [B70.md](B70.md) and the README say, and holds both families (`Q36=ON` is the default). One extra step for the
long-prompt attention (LP3, an AOT build for Battlemage): it compiles against two upstream projects that are not in this repository. Fetch them once (pinned commits, about 40 MB; [THIRD_PARTY_NOTICES.md](../THIRD_PARTY_NOTICES.md) has the
licences):

    bash sycl/tools/get-q36-tla.sh

Then, in the same container as the README's build:

    docker run --rm -u $(id -u):$(id -g) -v "$PWD/..:/work" -e AOT=bmg-g31 -e REPO=/work/$H \
        -e BUILD_DIR=/work/$H/build-sycl-aot strata-sycl-dev "cd /work/$H && bash sycl/tools/build.sh strata"

(`H=$(basename "$PWD")` as in the README.) The build makes `build-sycl-aot/strata`, `build-sycl-aot/libq36_w4.so` and `build-sycl-aot/libq36_tla.so` beside
it; the binary finds the libraries through its run path, wherever the folder is mounted. Without an `AOT` of
`bmg-*` or `lnl-*` there is no LP3 and nothing to fetch (the 8-bit cache's prompts then take the engine's own attention, slower).
With `AOT=bmg-...` and no fetched `third_party/`, `Q36_TLA=AUTO` (the default) builds `strata` without LP3 and says so in a NOTE
(`build.sh`) and a CMake WARNING; `Q36_TLA=ON` stops before it touches cmake and says to run the script; `Q36_TLA=OFF` never builds it.
`Q36=OFF` leaves the whole dense family out.

## Run

1. The tokenizer, once, from the GGUF (it writes `<out>/tokenizer/`, with the model's chat template):

       python3 tools/strata_tokenizer.py --gguf /path/to/models/Qwen3.8-27B-UD-Q4_K_M.gguf --out /path/to/data/qwen38-27b

2. A config: copy `tools/qwen35/serve-27b.json` (32,768 cells), `serve-27b-128k.json` or `serve-27b-256k.json` and replace the
   `/path/to/` placeholders (the model, its folder, and `<out>/tokenizer`). The model folder must be mounted into the container: `STRATA_SYCL_MOUNTS` names it, or keep it under the
   repository's parent folder (mounted at `/work`). The config carries `"STRATA_SYCL_NAME"`, the container's name; **give it a name of
   its own**, because `strata-sycl.sh` removes a container of that name before it starts one, and the default name is the one a
   Flash-Next server uses.
3. The server, from the repository folder:

       python3 serve/server.py --engine strata --config /path/to/serve-27b.json --port 8131

   The 27B takes up to 26.7 GiB of the card at 262,144 cells: stop a Flash-Next engine first. The server ends engines that an earlier
   server left running; `STRATA_KEEP_LEFTOVERS=1` turns that off, for a start beside another server.

The API name is `qwen3.8-27b`; its sampling defaults are the GGUF's (temperature 1.0, top-p 0.95, top-k 20 when thinking).
By hand, one prompt: `tools/qwen35/q36_sycl_run.sh --model <gguf> --tokens <ids|@file> --n 64` (`Q36_MODELS` names the model's folder).

## What it does

- **Cache.** FP16 K/V by default (69.6 KB a cell); the 8-bit cache (`--kv int8`, Flash-Next's int8 format: int8 codes with one FP16
  scale per 64 values) is the default above `--max-context 131072`. At 262,144 cells it is 8.77 GiB, and the engine fits the card.
  `STRATA_Q36_KV=f16|f32|q8` overrides the flag.
- **MTP draft.** The model's own MTP block drafts 5 tokens a step by default (`--mtp N`, 0-7; `--mtp 0` is plain decode), and
  fewer as the conversation grows: at most 4 from 16,384 cells in the cache, at most 3 from 32,768 (`STRATA_Q36_MTP_CELLS`; every
  column of the verify window reads the whole K/V cache). The draft block and the draft head are requantized to Q4_K at load
  (`STRATA_Q36_DRAFT_Q4=0`: as the file has them, Q6_K): a draft only proposes, so the text is unchanged. The draft
  head reads a 64K-token vocabulary (`tools/qwen35/q36_draft_vocab_64k.json`; `--draft-vocab`, `--draft-tokens`). The verify window
  gives the plain greedy decode's tokens (checked for `--mtp` 2 to 7 on the two localmaxxing prompts). What drafts is in "Drafting
  requests with a penalty or a temperature" below. The server's model-card set for thinking off carries `presence_penalty` 1.5;
  for this family the server leaves that penalty out when the temperature is 0 (a penalty the request, the config's `sampling`
  block or the Chat settings names stays). `STRATA_CARD_PENALTY_AT_GREEDY=1` in the server's environment keeps the card's
  penalty at temperature 0, as before 2026-11-11.
- **Decode.** Q4_K and Q5_K products, and IQ4_XS on the 17408-wide `ffn_down`, run on the card's matrix engine (the XMX rows
  forms, `q36_xr_dense.dp.cpp`; `STRATA_Q36_XR=0` turns them off): a hardware thread owns 16 output rows and one s8 `dpas` is the
  dot of 32 weights x 16 rows x up to 8 columns, so a draft more costs its float scaling and no second read of the weights. The
  other products run on the KREG kernels (on for this model; `STRATA_MMVQ_KREG=0` turns them off). GQA attention shared over the 6
  query heads of a KV head, decode-side GDN kernels, a prompt chunk of 2,048 tokens when VRAM allows (then 1,024, 512).
- **Long prompts.** For the 8-bit cache, chunks run through vllm-xpu-kernels' Xe2 `chunk_prefill` on sycl-tla (LP3): the layer's K/V
  is dequantized to FP16 in 32,768-cell segments, each segment's output merged by log-sum-exp. `STRATA_Q36_PATTN=lp2` keeps the
  engine's own flash kernel, `gemm` the GEMM path (FP16/FP32 cache only).

## The int4 pack, lookup drafts and the matrix-engine attention (2026-11-12)

A second set of weights for the same model: a GPTQ int4 checkpoint (4 bits, asymmetric, groups of 128 inputs, no
act-order; the format vLLM serves) packed for the card. The GGUF stays the source of everything else (norms, embeddings,
the head, the MTP block), and the GGUF path above is unchanged.

```sh
python3 tools/qwen35/b70w4_pack.py --ckpt <GPTQ checkpoint dir> --gguf <the model's GGUF> --out model.b70w4
strata --native <the model's GGUF> --w4 model.b70w4 ...
```

- **The pack** (`tools/qwen35/b70w4_pack.py`, about 12 GB): every big matrix as records of 16 output rows x 256 inputs. A
  hardware thread owns 16 rows and reads its records in order with block loads; 32 nibbles are one DPAS operand as they
  are. The tool checks each matrix against the GGUF's tensor of the same name (row correlation above 0.8, else it stops)
  and regroups the 48 GDN heads the way the GGUF conversion does.
- **Windows of 16 rows**: a pass takes up to 32 activation columns, so a step verifies up to 15 drafts (`--mtp 0..15`,
  default 15 with the pack). The depth follows acceptance: 5 at first, one more after a fully accepted step (two from 8
  on), back to max(5, accepted + 1) after a miss.
- **W4A16** (`q36_w4h.dp.cpp`; `STRATA_Q36_W4A16`: `1` on, `0` off; unset: on for a batch engine): the pack against FP16
  activations, the form vLLM runs. The int8-activation form pays float work per column and 32 weights (the activations'
  scale per 32 values, the zero times their sum): 5120 x 17408 takes 82.7 / 93.6 / 115.1 / 184.3 us at 1 / 8 / 16 / 32
  columns. With FP16 activations a sub-block's 32 nibbles become 32 half floats (q - zero, exact) in two DPAS operands,
  8 columns' activations for 16 inputs are one block load, and a row's scale is applied once per 128 inputs: 87.2 / 90.0 /
  93.9 / 114.8 us. A column costs 0.9 us instead of 3.3. Both are within 1.5e-7 of a float64 model. A single session keeps
  the int8 form for now: its usual 6 rows gain nothing and the FP16 images are 3 more launches a layer (8 requests: 104.0
  -> 100.3 tok/s), while an edit's 16-row windows gain (287 -> 317 with `STRATA_Q36_W4A16=1`).
- **Lookup drafts** (`STRATA_Q36_NGRAM=0`: off): when the model is copying an earlier part of the conversation, the next
  window's drafts are the tokens that follow there and the MTP block drafts nothing that step. A copy starts after 5
  tokens of an MTP step were an earlier place's continuation, keeps a cursor in its source, and after a break takes one
  MTP step and lines up what the model wrote with the source (up to 4 tokens written for up to 3 of the source's). One
  source token that became others is remembered (a rename). The verify window decides as for any draft: texts are
  identical with the switch off, greedy and sampled.
- **Decode attention on the matrix engine** (`STRATA_Q36_XATT`: `1` on, `0` off; unset: on, for the GGUF path as for the
  `--w4` pack, when the engine's shape allows it (head dim 256, 6 query heads a KV head; multi-session batches controlled by
  `STRATA_Q36_XATT_BATCH`, default on) and what it needs fits beside all sessions' caches with 2 GiB of VRAM to spare; one
  rule at one place in `Engine::init`, which also decides the 8-bit cache's V layout for every session together). Until
  2026-11-13 the default was on only with the pack, so a GGUF start answered 49% slower than it had to after a long prompt
  (numbers below), and multi-session batches stayed on the FP32 kernel. If the fit fails (for example, FP16 caches with one
  mirror per batch slot exceeding VRAM), the engine does not fail to start: the log says "decode attention stays on the FP32
  kernel" and every session keeps the plain layout. An explicit `1` skips the 2 GiB spare check when VRAM still holds the
  allocations. The FP32 kernel is compute-bound at long context (a 5-token window at 25K cells: about 16 ms of a 51 ms
  step). `q36_xatt.dp.cpp` does scores and value sums with DPAS on a mirror of each attention layer's cache: K as int8 with
  one scale a cell and KV head, V as int8 transposed in blocks of 32 cells, probabilities as 16-bit integers. In a batch or
  `--batch-mtp` window (`n_sess > 1`), `attn_core` runs one sequential `attend()` call per XATT-eligible slot over that slot's
  contiguous rows and own cache/mirror pointers, reusing the single call scratch on the in-order queue (`run_rows` and
  `mtp_rows`; any slot below threshold, near context end, or above `xls_max` tokens uses `k_attn_gqa` for its own rows,
  and graphs are keyed per slot slice when any slot uses it). It starts at `STRATA_Q36_XATT_MIN` cells (4096); a non-`kv_vt`
  session mirror catches up when its conversation reaches the threshold, and `copy_session` copies transposed V blocks +
  scales when `kv_vt` is on. Chunks and the merge are the FP32 kernel's, and a row's result does not depend on its window.
  This path is not bitwise the FP16 cache: teacher-forced over 97 tokens after an 8K prompt, mean KL 0.00022 against it,
  top-1 100% (the engine's 8-bit cache: 0.00018, 100%). The mirror: 1.08 GiB per session at a 32K FP16 context (so 4 slots
  take ~4.3 GiB of mirrors on top of FP16 KV and fall back to FP32 on a 32 GB card). With the 8-bit cache (a context past
  131,072, or `--kv int8`) there is no mirror for any slot: the scores read each session's own K (a scale per 64 values),
  and the cache stores V transposed with one scale a cell (`STRATA_Q36_KV_VT=0`: V cell by cell and a transposed copy,
  4.3 GiB per session at 262,144 cells). The cache's other readers take that layout: the store, the FP32 decode kernel, the
  prompt path's staging and dequantize. Against the plain 8-bit cache, through each of them: mean KL 0.0002, top-1 100%.
  At 262,144 cells the attention then costs only 0.77 GiB of shared call scratch across all slots (0.12 GiB at 32K, 0.21 GiB at 64K).

## Drafting requests with a penalty or a temperature

Until 2026-11-11 only a greedy request without a penalty drafted: the window's picks were the device argmax of the raw logits. A request
with a presence, frequency or repeat penalty, and every request with a temperature above 0 (the default of every client that does not
say 0), ran one token a step. They draft now. **Written from reading the code and run on the host only; not run on the card: no speed
and no text of this path was measured.**

- **How.** The draft is the draft head's argmax, one token. The verify window returns, for each of its rows, the M highest raw
  logits (a two-stage top-M kernel pair in a second graph variant of the window; the greedy graph is not touched; one copy of
  at most 8 KB for the window). The host then does what the one-token-a-step path does with a whole row, on that list: applies the penalties
  to the listed tokens that are in the row's window (the last `penalty_last_n` tokens, then the accepted drafts before the row),
  ranks by (logit, lowest id), keeps the sampler's cap (`top_k`, 64 if 0), applies temperature, min_p and top_p and draws once from the
  request's own random stream (a temperature of 0 takes the argmax, no draw). Row 0 is drawn first; the draft is kept when it equals the
  draw, then row 1 is drawn, and so on; the first row that does not match ends the window, and its draw is the next token. The commit of
  the accepted rows is the greedy path's. Source: `sycl/src/qwen35/q36_sampling.hpp` (the host side, shared with the plain path) and
  `sp_topm` / `spec_step_g` in `q36_engine.dp.cpp`.
- **What is exact.** Every emitted token is one draw of its row's target distribution given the tokens before it, the draw the plain
  path makes, so the output distribution is the plain path's whatever the draft is (a rejected draft costs speed only). A draft is kept with
  probability p(d), the target's probability of it: for a point-mass draft that is the Leviathan rule min(1, p / q) too. The stream is used
  once per emitted token, in order, so with the same seed the text equals the plain path's text if the window rows' logits equal the
  single-step logits bit for bit (that is what `STRATA_Q36_DUMP_MTP` was made to check for the greedy path; not run for this one).
  A seeded request is reproducible in any case. A request without a `seed` uses the stream of seed 0, as before.
- **What drafts.** Needs the graph form of the window: one session (no `--batch`; the batch window is the next section), no hybrid experts, graphs on, `--mtp` 1 to 7. Penalties
  that only lower a logit (`repetition_penalty` at least 1, frequency and presence at least 0) with a window of 1 to 64 tokens (the server's
  default is 64), and a cap of at most 64 (the server clamps `top_k` to 1..64). The window of a row then needs at most cap + 64 raw
  candidates (at most 128); that bound is what makes the host's list the plain path's list. Other requests keep the plain path: a
  penalty that raises a logit, a window over 64 or of the whole history, `top_k` above 64 sent to the engine directly.
- **Cost.** The top-M kernels run after the verify window and their cost grows with M (cap + window): an estimate, not a measurement,
  is 0.3-1.5 ms of a 40 ms step. The host's draw of a row costs about what the plain path's host sampler costs, without its 1 MB copy.
- **The one change to the plain path:** its candidate order is (logit, lowest id), so an exact tie no longer depends on
  `std::partial_sort`. Nothing else of it changed (`tools/test_q36_spec_sampling.py` runs the old code beside it).
- **Tests without the card:** `python3 -m pytest tools/test_q36_spec_sampling.py -q` (g++): the float keys, the kernels' algorithm run on
  the host against a sort, a window row against the plain sampler, a whole answer through windows against the plain loop for the
  same seed, the accept / reject rule against a known distribution, the point-mass case of the Flash-Next rule. They do not run the
  kernels. `STRATA_Q36_SPEC_CHECK=1` makes the engine compare each window's rows with the host's top M of the whole row and print a
  mismatch (it copies the rows: slow).

### In a `--batch --batch-mtp` window (written from the code, not run on the card)

Until this change a request with a temperature or a penalty got no draft in a batch window: its slot had one row, one token a window,
and the host drew from the whole row (a 1 MB copy and a wait a slot), while the greedy slots beside it drafted. With
`STRATA_Q36_BATCH_SAMPLE=1` such a slot drafts like a greedy one:

- **Rows.** The slot's rows are the same as a greedy slot's: its next token, then the MTP block's chained drafts (greedy picks of
  the draft head). `fit_depths` shares the 16 rows of the window as before; a sampled slot asks for the same depth a greedy slot does.
- **Candidates.** The window runs the two top-M kernels of the one-session window over all its rows (a graph of its own, key
  410000; the window without them is not touched) and copies the lists back in the same wait as the picks: one copy of at most
  16 KB for the whole window, no wait a slot. M is the largest any drafting slot needs (`top_k` capped at 64, plus the penalty
  window); a slot reads the first M of its own, which is its own list. Greedy rows in a mixed window get their lists too (not
  needed, not measured: the cost of the top-M for 16 rows instead of 6 is an estimate only).
- **Draw.** Per slot, the host runs the single-session code (`decide_window`, `q36_sampling.hpp`) on the slot's own sampler,
  history and random stream: row 0 is drawn, the draft is kept when it equals the draw, then row 1, and so on; the first miss ends
  the slot's window and its draw is the next token. One draw a token, in order, so what one slot draws does not depend on what
  shares the window or on the depth it got. The kept rows are committed with `commit_rows`, as for a greedy slot.
- **Not drafted** (the slot keeps one row and the host draw of the whole row): the requests `spec_plan` refuses (a penalty that
  raises a logit, a penalty window over 64, `top_k` over 64), `STRATA_Q36_SPEC_SAMPLE=0` for sampled and `STRATA_Q36_SPEC_PEN=0`
  for greedy-with-penalty requests, a hybrid-expert engine.
- **What is exact.** Given the same logits, the same token from the same stream. The host test
  (`tests/core/q36_spec_sampling_test.cpp`, "slots of one batch window") runs 2 to 8 slots with their own samplers, seeds and
  depths, greedy and drawn slots together, an end token and `max_new` inside a window, and compares each slot with the same
  request alone one token a step. Whether the logits of a window row are the same bits as the logits of a one-row step on the
  card is not known (the column count picks the kernel form): the first check on the card is the text of a request alone against
  the batch.
- **Off by default** until it was run on the card. How to measure it: `REPORT.md` and `tools/q36_batch_sample_check.py`.

## Not done

- Deeper drafts at long context do not pay yet (full depth instead of 4 / 3 past 16K / 32K cells: prose after 25K 67.1 ->
  65.3, the 118K prompt's answer 49.4 -> 46.3).
- The same attention's kernels are not at the memory limit: a call at 25K cells takes 160 / 228 / 572 us for 1 / 5 / 16
  tokens. The score kernel's time barely depends on the row count (not explained), and the value kernel ends with 64
  scatters a thread (70 of its 128 us at 5 tokens: its sums should leave as blocks, with a merge kernel that reads them).
- Requests at once: 4 requests reach 182 tok/s in all with `--batch 4 --batch-mtp` (community vLLM setups: about 290).
  vLLM's streams each keep their full draft depth, because a batch is only more rows in every product and its rows are
  cheap (FP16 activations). Here a row cost about 1.7 ms (2 requests, depth floors 1 / 3 / 5 / 7: 27% fewer windows, each
  33% dearer, the same throughput), 1.0 ms of it the int8-activation product's per-column work, which W4A16 removes.
  What is left, measured on a window of 4 requests (49.5 ms for 10.4 tokens): the window 41.5 (the weights about 29 at
  16 columns, the GDN layers' states of 4 sessions 3.9, the head in two passes 3.8, small kernels and the FP16 images
  about 5), the GDN states' commit 4.2, the next drafts 3.8 (one call a draft level, each with a wait). Next: windows of
  32 rows (the kernels of a decode window are sized for 16: `kVerify`, `kGemmT`, `kDecT`), the 17408-wide matrix at 32
  columns (199 us: its tiles need more threads), a head form that takes 16-32 columns in one pass, the draft calls and
  the window as one graph, the FP16 images written by the kernels that already write the q8_1 ones.
- Code is the slowest of the tests above (113.6): MTP drafts are accepted about 62% of the time there and a step costs
  about 37 ms (body 25, draft calls 0.78 each, head 2, about 700 small launches 6).
- The sampled draft is the head's argmax; drafting from the head's distribution with min(1, p / q), as the Flash-Next engine does,
  needs the draft head's top list on the device and is not built. The cost of the top-M kernels alone was not measured.
- IQ4_XS on the 5120- and 6144-wide matrices (about a third of the main model's bytes) stays on the KREG forms: its codebook
  lookups make the XMX form 5-12% slower there, and at 5-6 columns the KREG forms cost 7-9% more than at 4. An exact decode of
  the codebook without lookups was worked out (about 340 instructions per 32 weights) and is too slow. Q6_K, Q3_K and IQ4_NL
  have no XMX form: their 17408-wide rows are read twice at 5 or more columns.
- Tried on 2026-11-12 and not kept: a lane per output row with plain dot products, activations reloaded per tile (from the
  buffer or from shared local memory), loads issued one block ahead into registers (prefetch is faster), a 32K draft
  vocabulary (reasoning 75.3 tok/s), a draft depth that follows the last step's acceptance (82.2-83.6 / 64.9-66.9).
- Reading a long prompt: 1,096 tok/s at 118K is over the bar (2026-11-11); 721 tok/s at 256K (2026-11-03) is 28% under it. The
  prompt attention was the last part replaced (LP3); what is left in it was not measured.
- Answers after a long prompt: the 118K run offered no drafts at all (0 of 0) and answered at 21.5 tok/s. The cause was not
  the context: that request had thinking off, so the server added the card's `presence_penalty` 1.5 to its temperature 0, and a
  request with a penalty is not drafted. Fixed in the server (see "MTP draft"). Measured after the fix: 31.0 tok/s with 428 of
  771 drafts accepted, against 21.5 without drafts. That is under the 37 to 63 tok/s the step arithmetic gave (a step of 52 to
  54 ms, 2.0 to 3.3 tokens a step); the step at 118K was not profiled.
- Sampled requests (temperature above 0, which is every request that leaves out `temperature`: the card's default is 0.7 or
  1.0) are never drafted: plain decode, about 27 tok/s at short context (2026-11-03) and 21.5 at 118K. Drafting for them needs a
  sampler that runs on the device for every row of the verify window; it is not built.
- The Q5_K and IQ4_XS matrix-vector kernels are the least efficient of the formats the model uses (about 81% and 68% of the card's
  bandwidth at the last measurement).
- Q3_K and IQ4_NL matrices (4.6% of the weights in UD-Q4_K_M, 2.9% in UD-Q4_K_XL) are dequantized for a prompt by the plain kernel, not
  the wide one the original branch had. From that kernel's measured rates (165 against 485 GB/s) this costs about 10 ms a
  prompt chunk on UD-Q4_K_M (about 0.5% of a 2,048-token chunk at 1,100 tok/s, about 2% of a 300-token prompt): an estimate, not a measurement.
- One request at a time was measured. `--batch N` exists in the engine and was not measured; this fork's rule is one stream.
- Pictures (`--vision`) are wired in the engine and were not tried.
- The server's disk sessions (`SAVE` / `RESTORE`) and `VRAM` commands (`POST /v1/vram`, `vram_elastic`) are not implemented in the
  engine: it answers `ERR`, and the server then ends the engine and starts it again. Leave those features off.
- Qwen3.6-35B-A3B (`qwen35moe`) is in the engine's source and is not built or run here.

## Reading the source

Comments in the engine's sources name the steps the engine was made in: M2 the decode and MTP kernels (an FP16 cache and the GQA
attention too), M3 the prompt path, the serve wiring and 128K, M4 the 5-8 column windows and the long-prompt kernels. LP2 is the
engine's own head-256 prompt attention for the 8-bit cache, LP3 the `chunk_prefill` one that replaced it as the default.
